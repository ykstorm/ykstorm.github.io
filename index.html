Homesty

Answers that come from the real listing

Next.js, React, Node, Postgres, Prisma, Vercel, Sentry

homesty.ai

The problem

People buying a flat ask narrow questions: when possession is due, which configurations exist, what a project actually includes. A chat reply that sounds right but didn't come from the listing is worse than no reply, because the buyer acts on it.

How it works

A buyer asks about a project in the chat. The question goes to a Node REST API, which reads that project's listing records from Postgres through Prisma, and the reply is built from those records.

The team keeps the records current in an admin area behind sign-in. Every change is written to an audit log: who made it, what changed, when, and the record version. So the answer a buyer sees comes from the same records the team edits, and each edit can be traced.

What shipped

I've been building Homesty since November 2025: the landing page, the buyer chat, the REST API, the admin area, auth, and the audit log. It's live at homesty.ai, deployed on Vercel, with errors reported to Sentry.

Anchor, further down, is the retrieval idea from Homesty pulled out into its own tool: when the sources don't cover the question, say so.

Anvil

Webhooks that run once

TypeScript, Redis, BullMQ, Docker

GitHubnpm

The problem

A webhook provider retries when it doesn't hear back fast, and re-sends events it isn't sure you got. Meanwhile your handler can crash halfway through a job. Without care, the same payment or signup is processed twice, and the jobs that keep failing have nowhere to go.

How it works

  • Check the signature first. Recompute HMAC-SHA256 over the raw request bytes and compare with crypto.timingSafeEqual after a length check. A bad, missing or malformed signature gets 401 and nothing is queued.
  • Claim the delivery. The idempotency key is sha256(signature header + raw body). The first delivery claims it with an atomic SET key 1 NX EX ttl (one week by default), enqueues one BullMQ job, and returns 202 with the job id. A repeat finds the key taken and gets 202 with replayed: true and the same job id. Two copies arriving at the same moment still make one job.
  • Retry on a fixed schedule. A failing handler gets four attempts in all, with waits of 1s, 5s and 30s between them.
  • Park what never succeeds. After the fourth failure the job moves to webhooks.dead with its attempt count and last error, truncated, with credential-looking query params redacted.
  • Replay by hand. replayDeadLetter(jobId) moves one dead job back to the main queue with a fresh retry schedule. It starts no worker, so importing it can't kick off a retry loop.

What shipped

Published on npm as @ykstormsorg/anvil. The SDK exports three functions: createServer, createWorker and replayDeadLetter, and the repo has tests for each behavior above.

What it doesn't do

The HMAC covers the body only, so a captured request can be replayed after its key expires. If your provider signs a timestamp, check it in your handler. A provider that changes the signature on re-delivery produces a new key; deduping on a provider event id is out of scope. One Redis, one region. Replay is one job at a time, with no batch tool or UI yet.

Anchor

Retrieval that admits when it has nothing

TypeScript, Next.js, Postgres with pgvector, Prisma

GitHubPlayground

The problem

Most retrieval examples hand the top few chunks to a model however weak the match. A chunk with a cosine similarity of 0.12 to the question isn't a basis for an answer, but a top-k pipeline passes it along anyway, and the model writes something plausible, cited and wrong.

How it works

Anchor embeds the query and runs a cosine-similarity search over a pgvector table for the top candidates, six by default. It notes the best similarity it saw, then drops every chunk under the floor, 0.30 by default.

If chunks remain, it returns them with the source of each one. If none remain, it returns an empty list with refused: true, plus the floor and the best similarity, so the caller can tell a real miss from a weak guess. Nothing in the query text can lower the floor. No model is called here; this is the layer a model would sit on.

What shipped

A Next.js app with a query API and a playground that runs against a seeded demo corpus, so you can watch a question get answered or refused.

What it doesn't do

The 0.30 floor is a property of the corpus, not a constant. It separates answerable from unanswerable questions on the seeded demo set; another corpus needs its own number, found by comparing similarity scores for questions you know are answerable against ones you know aren't.

Tripwire

Streams that stop themselves

TypeScript, Express, OpenAI-compatible proxy

GitHubnpm

The problem

A streamed reply is on the user's screen as it's generated. If a model leaks an API key, a phone number or a discount nobody approved, a check that runs when the response finishes is too late. The leak can also be split across chunks, "call " then "98765" then "43210", and checked one chunk at a time, none of them looks wrong.

How it works

Every chunk is appended to a raw buffer and a normalized copy, and the rules run against the normalized text on every chunk. The guard holds back the last 48 characters before releasing anything, so a match that straddles chunk boundaries is still inside the tail when it completes.

If a hard-abort rule matches (a secret, contact or business leak), the guard throws GuardAbortError and latches, and the held tail is never sent. As a proxy, Tripwire speaks the OpenAI chat API, so an app only changes its base URL; on a trip it sends a rule_trip event and closes the stream. If nothing trips, everything except the tail is released, and flush() sends the tail at the end.

What shipped

Published on npm as @ykstormsorg/tripwire, as a library you call at the stream site and as the proxy you run beside your app. A post-hoc mode, checkResponse, runs the same patterns over finished responses for batch review.

What it doesn't do

It's regex. It catches mechanical leaks such as keys, phone numbers, email addresses and fixed phrases, not a paraphrase that matches no pattern. Output also trails the model by the hold-back length, 48 characters by default.

Stackup

Canary deploys gated on real traffic

kind, ArgoCD, Argo Rollouts, Prometheus, Grafana, Helm

GitHubDocs

The problem

I wanted the whole progressive-delivery loop, GitOps sync, canary steps and a metric gate, running on a laptop rather than on a managed cluster that bills by the month.

How it works

A push changes what the cluster should run. ArgoCD, set up as one root app managing six child apps, syncs it with automated prune and self-heal. Argo Rollouts moves 25% of traffic to the new version, pauses, and runs an analysis: Prometheus computes the share of 2xx responses in http_requests_total over a two-minute window, three times, 30 seconds apart.

At 0.95 or above, the rollout moves on to 50, 75 and 100%. A failing analysis is meant to abort the rollout and send traffic back to the stable version.

What shipped

make up builds the stack on kind; the README puts it at roughly 12 to 15 minutes, which depends on your machine and how much has to download. It also sets up cert-manager TLS, Sealed Secrets, Calico network policies and Pod Security restricted on workload namespaces.

A separate CI job builds a kind cluster with a live Prometheus, drives real traffic, and watches a 25, 50, 75, 100% canary advance only because the measured ratio clears 0.95. No mocked metric.

What it doesn't do

The rollback isn't proven yet. CI only runs the passing path, and failureLimit is currently equal to the number of checks, so failing checks alone can't fail the analysis. Lowering it and adding a run that forces a failing canary is the next change. Logs and traces (Loki, Tempo) are on the roadmap, not installed.
